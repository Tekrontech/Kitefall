**Rule:** Do not rewrite working systems. Add new classes, extend existing ones, keep `Core/` pure C# and unit-tested.

### 0.1 How to build the visuals
- **Humanoid characters:** start from Unity's free *Starter Assets – Third Person* humanoid (Asset Store, by Unity Technologies) with its idle, walk, run, jump and land animations. Give each character a **distinct look**: proportions within humanoid limits, skin/hair colours, and clothing built from separate meshes (kurta, jacket, cap, scarf, shoes) with cloth-like materials. Outfits and accessories = swappable mesh parts with their own materials.
- **Animation:** use the **Animation Rigging** package for pull, dheel, reel, kanni tying, toss, tugs, climbing and emotes — two-bone IK keeps the hands on the string and the charkhi, multi-aim makes the head follow the kite; author extra clips in Unity's Animation window where needed. Movement must look smooth and natural, with blending between states.
- **Kites:** detailed meshes (sail, bamboo sticks, bridle), paper/fabric Shader Graph with translucency against the sun, wind flutter in the vertex shader, ribbon tails.
- **Arenas:** ProBuilder or procedural meshes for houses, roofs, parapets, stairwells, water tanks, charpais, cables, bridges, ladders and planks; procedural textures (brick, plaster, concrete, wood) generated in Shader Graph; variety in colours, windows, doors and clutter so roofs feel lived-in.
- **Sky & light:** gradient sky shader with sun disc, animated clouds, golden-hour colour grading, time-of-day per match.
- **Effects:** line glint, contest sparks, snap flash, paper fragments, gust streaks, storm wall, crate balloons — particle systems with soft additive materials.
- **UI:** clean, modern, consistent; rounded panels, icons drawn with vector-style sprites generated in code or simple SVG imports; smooth screen transitions and button feedback.
- Keep every visual inside its view/factory class (`CharacterView`, `KiteVisualFactory`, `ArenaBuilder`, `PropFactory`, `Effects`), separate from gameplay code.

## 1. Weakness fixes (do these first)

### W1 — Visible humanoid characters replace `FlyerView` primitives
- New `Match/CharacterView.cs` (MonoBehaviour). On `Init(anchor, characterId, outfitId, accessories, teamColor)`:
  1. Spawn the humanoid (section 0.1) with the selected character's look and outfit parts; keep `FlyerView` only as a safety fallback if the model fails to load.
  2. Add an `Animator` with a controller built by an editor script (`Editor/CharacterAnimatorBuilder.cs`): states Idle, Walk/Run (blend on `Speed`), Jump/Land, Pull, Dheel, Reel, Launch, Win, Lose, HitReact, every prep step, climbing, and an Emote layer — clips + Animation Rigging IK (section 0.1).
  3. Attach accessories to bones by slot: Head → `Head`, Eyes → `Head` (offset), Back → `Spine2`, Waist → `Hips`. Attach a detailed charkhi model (per charkhi type) to `RightHand`.
  4. Expose `LineAnchor` = a child transform at the left hand. **The kite line must start from `LineAnchor`**, not the old fixed anchor point (update `KiteView`/line drawing to read it each frame; the server keeps using the arena anchor for physics — visual offset only, max 1.5 m).
- Animator parameters: `Action` (int: 0 idle, 1 pull, 2 dheel, 3 reel), `Launch` (trigger), `Win` / `Lose` / `HitReact` (triggers), `Emote` (int, −1 none), `Speed` (float, waiting area walking).
- Map from the existing `KiteSnap.Action` exactly like `FlyerView.Apply` does today.
- Name tag above every character (TextMesh/world-space UI): player name, team colour, squad icon. Hidden for the local player.
- `MatchPresenter` creates `CharacterView` instead of `FlyerView`.

### W2 — Third-person "shoulder" camera (PUBG-style)
- Add `CameraMode.Shoulder` to `MatchCamera`, and make it the **default during flight**:
  - Position: behind and right of the local character: `characterPos + back·4.5 + right·1.2 + up·2.0` where *back* points away from the kite (yaw only).
  - Look target: `Vector3.Lerp(characterHead, kitePos, 0.85)` — the character is in the lower-left third, the kite in the upper-right of the frame.
  - If the kite leaves the view frustum, widen FOV up to 70° before moving the camera.
- `CameraMode.KiteCam` = today's Follow mode (renamed internally, keep the old enum value for compatibility).
- **Auto-switch**: on `APPROACH` or `CUT_CONTEST` → blend to KiteCam over 0.35 s; 1.5 s after the contest ends → blend back to Shoulder. Cut slow-motion and replay keep their current behaviour.
- New Settings option *Camera style*: `Auto (default) / Shoulder only / Kite only`, saved in `SettingsService`.
- Add a small "camera" button on the HUD (top-left, next to Menu) that toggles Shoulder ↔ KiteCam for 10 s (manual look).
- Acceptance: in every mode, the local character is visible ≥ 90% of non-contest flight time; the kite is never off-screen for more than 0.5 s.

## 3. Feature F2 — Squad / party lobby

**Goal:** friends form a party in a lobby, then queue together.

- Party = a separate Multiplayer Services **session** (no Relay, lobby data only), max 4 members, leader = creator.
- Join by: friend list invite (Inbox message + push), 6-character code, share link (WhatsApp) → deep link `kitefall://party/<code>`.
- **Squad lobby screen** (`UI/Screens/SquadLobbyScreen.cs`): 4 spots on a rooftop stage with each member's `CharacterView` + name, rank, ready tick; crown icon on the leader; leader picks mode; members tap Ready; leader taps PLAY.
- Matchmaking with a party:
  - Team Battle: whole party on the same team; fill the rest.
  - FFA / Last Kite Flying: party members enter the same match (not teammates unless a future "squad LKF" mode).
  - Quick Duel / Ranked Duel: party size must be 1 → show "Leave party or choose another mode". Private Room: party joins together.
- Party chat = quick chat (F7) + party voice channel (F7).
- Party stays together after a match ends (return to Squad lobby).
- Acceptance: 4 phones form a party, queue Team Battle, land on the same team, return to the lobby together.

## 4. Feature F3 — Pre-match waiting rooftop

**Goal:** while the room fills, players are together on a big rooftop plaza (like a waiting island) and can move, emote and practise.

- New match phase `Warmup` **before** the existing `ArenaIntro` (add to `MatchSimulation` phase order). Duration: until the room is full or 45 s (Remote Config), min 10 s. Skipped in Quick Duel vs bot and Tutorial.

- Movement: on-screen joystick moves the character (`CharacterController`, walk/run anim by `Speed`). Server-authoritative position at 10 Hz is enough (no combat here).
- Practice kite: each player can fly a kite; **contacts are disabled** in Warmup (lines pass through; no inventory use, no durability loss).
- Emotes and quick chat allowed. Countdown banner "Match starts in 0:12 · 7/8 players".
- On end: fade → each player teleported to their arena anchor → normal ArenaIntro.
- Acceptance: 8 players see each other walking and emoting; no dor/kite is consumed in Warmup.

## 8. Feature F7 — Quick chat & voice chat

- 8 preset messages with icons: Go up! · Help! · Attack him · Defend me · Crate here! · Nice cut! · Thanks · GG. Localized via the existing string tables.
- In match: team-only in Team Battle; everyone in other modes (can be turned off in Settings). In party lobby: party only.

- Data: Vivox login with the Unity Authentication player id. Check Vivox pricing/free tier before launch.
- Acceptance: a party of 2 hears each other in lobby and Team Battle; strangers never hear them.

## 10. Feature F9 — Rooftop choice & roof hopping (complete, one build)

**Goal:** players choose their own rooftop before the match (like choosing a landing spot), and in big modes can **move to another roof during the match** — packing up the kite, running, climbing and jumping across the rooftops, then launching again.

### 10.1 Rooftop network (replaces the fixed row in `ArenaLayout`)
- `ArenaLayout` generates a **roof graph** per arena from the seed:
  - `RoofNode { id, center, size, height, traits[], capacity, neighbors[] }`, `RoofLink { a, b, kind: Plank | RopeBridge | Ladder | Stairs | Jump, length, travelTimeSec }`.
  - Roof count = `ceil(players × 2.5)` (min 6). Heights within the arena's range; at least 30% low, 30% high.
  - Every roof reachable from every other (connected graph); 1–3 links per roof; links ≤ 18 m.
  - Mirror symmetry option for Duel modes (left/right halves identical).
- Keep `a.Anchors` for compatibility: the anchor = launch spot on the chosen roof (centre, 1.35 m above the roof).
- Visuals: `ArenaBuilder` builds roofs, parapets with gaps where links attach, and link objects (planks, rope bridges, ladders, stairwell huts) as proper modelled objects (ProBuilder/procedural meshes with materials).

### 10.2 Roof traits (balance — no roof is simply best)
| Trait | Benefit | Cost | Default numbers (Remote Config) |
| --- | --- | --- | --- |
| High | Start/launch height +15 m | Gust strength ×1.25 at this roof, visible on everyone's radar | height ≥ arena max − 3 m |
| Sheltered | Gusts ×0.6, launch never fails | Start height −10 m; cables/walls nearby (crash risk) | ≥ 3 walls/buildings within 12 m |
| Upwind | Wind factor +3% in contests for the first 60 s | Open: approach ring range 20 m instead of 15 m (enemies notice you earlier) | in the upwind 25% of the map |
| Crate spot | First crate of the match drops within 40 m | Everyone sees it on the map → crowded | 1–2 roofs |
| Edge | Fewer neighbours, calmer start | Storm zone reaches it first (LKF) | outer 15% of the map |
| Cables | — (map hazard) | Lines can snag (untangle mini-game, section 11.4) | power cables crossing above |

Rules: a roof can have 0–2 traits; never High + Upwind together. Track win-rate per trait (analytics) and tune; target every trait 45–55% when equal skill.

### 10.3 Rooftop selection phase
- New phase **`RoofSelect`** after matchmaking/Warmup, before `ArenaIntro`: **15 s** (Duel 8 s).
- Screen: top-down arena map drawn from the roof graph with roof icons, each roof shows traits on tap. Teammates / party members are shown on the map.
- Tap a roof → claim it (server decides on conflicts: first request wins; taken roofs show a lock). Can change until the timer ends.
- No choice → server assigns a free roof (prefers the roof with the fewest nearby players).
- Capacity: FFA/LKF 1 per roof; Team Battle up to 2 teammates per roof, never enemies on the same roof.
- Mode rules:

| Mode | Selection | Roof hopping |
| --- | --- | --- |
| Ranked Duel | Server assigns a random **mirrored pair** of roofs (both identical); the screen shows both roofs so players still see the map | No |
| Quick Duel | Pick one of 3 mirrored pairs | No |
| Free-for-All | Free choice | Yes |
| Team Battle | Team half of the map, free inside it | Yes (inside own half for the first 2 min) |
| Last Kite Flying | Free choice on the big map | Yes |
| Private Room | Host chooses: Free / Fixed | Host option |
| Training | Any roof | Yes (to practise) |

### 10.4 Roof hopping (during the match)
Flow: **Pack up → Move → Prep & launch (short)**.
1. **Pack up:** button "Change roof". Fast reel animation brings the kite down in 3–5 s (depends on line out and charkhi reel speed). While packing the kite **can still be contacted** (risk!). Cannot pack up during a contest.
2. **Move:** the character walks/runs (joystick) with the kite in hand. Links: plank (balance walk, slower), rope bridge, ladder (climb up/down anims), stairs, small gap jump. Parapets: vault. Travel times from the `RoofLink` data (3–10 s each).
3. **Arrive:** an empty roof (or a teammate's roof in Team) → "Launch here" → **short prep** (section 11.5).
- **No hiding:** while grounded you score nothing (FFA), the storm still hurts (LKF), and after **25 s grounded** the game auto-starts a short prep on the current roof.
- Falling: characters cannot fall off roofs (invisible guard rails) — no death mechanic; the kite is the only "life".
- Network: character position/state server-authoritative at 10 Hz; link traversal is a server-timed action (`TraverseLink(linkId)`), the client only animates it → no teleport cheats.
- Bots: `BotBrain` gets a `ChangeRoof` decision (Retreat state when outnumbered nearby or storm approaching), using the same rules.

### 10.5 Acceptance
- FFA with 8 players: everyone picks different roofs in 15 s; at least 2 players change roof during the match; no player can stay grounded > 25 s.
- Duel: both players always start with equal height and wind.
- Bot vs bot simulations: no trait above 55% win-rate over 1,000 matches.

## 11. Feature F10 — Kite preparation & launch ritual (patang charhana)

**Goal:** the moment before flying becomes a short, beautiful, skill-based ritual on the rooftop — fully animated — replacing today's 5 s "HOLD to launch".

### 11.1 The sequence (round start: up to 25 s)
| Step | What the player sees | Player input (mini-game) | Animation | Result |
| --- | --- | --- | --- | --- |
| 1. Pick kite | Character takes the selected kite from the bag, checks it (durability shown; tears visible) | none (auto, 2 s) | pick up + inspect | — |
| 2. Kanni bandhna (tie the bridle) | Close-up on hands tying the bridle; balance indicator | **Timing ring**: tap when the needle is in the golden arc, 2 taps | kneel and tie bridle | Kanni balance: Perfect / Good / Off |
| 3. Dor jorna (tie line) | Knot animation, charkhi in the other hand | auto (1.5 s) | tie knot | — |
| 4. Chhudaai (toss) | **Helper** walks back 10–15 m holding the kite up, line stretched; or solo hand launch | Hold PULL → release when the toss ring is golden (same as today's perfect window: 1.2–1.6 s) | helper walks back, holds up, tosses / solo hand throw | Start height: Perfect +10 m, Good +5 m, Miss = kite dips, retry (−3 s) |
| 5. Tunke (climb tugs) | Kite low above the roofs; nose swings; ring pulses | Tap PULL in rhythm when the nose points up (3–5 tugs) | short tug | Each good tug +4 m climb; bad tug −2 m |
| 6. Dheel & climb | Line pays out, camera rises with the kite, music builds | free steering | idle → flight anims | Ready: normal flight, Shoulder camera (W2) |

### 11.2 Effects of the results (small, skill-based, identical rules for everyone)
- **Kanni balance**: Perfect = no drift. Good = slight drift (0.5°/s) until the player steers once. Off = drift 1.5°/s for the first 20 s. **No effect on contest Power.**
- **Start height** = base + toss bonus + tug gains, **capped at +20 m** above base.
- Total prep time is capped: whoever finishes early simply starts flying earlier (positioning advantage, already part of the spec's "perfect launch" idea). Unfinished at the cap → game auto-completes with "Good" results.
- **Auto-prep setting** (Settings ▸ Gameplay, default off; on for players flagged as new during their first 5 matches): plays the full animation automatically with "Good" results. Ranked allows it (Good is never better than a skilled Perfect).

### 11.3 The helper (chhudaai wala)
- Solo players: an NPC helper (a humanoid in a simple festival outfit) appears on the roof, does the toss, then walks to the stairwell and leaves.
- **Team / party: a teammate on the same roof can be the helper** — a "Help launch" button appears when a teammate is preparing within 15 m. The helper performs the toss timing; a Perfect toss by a teammate gives the launcher +2 m extra and both get a small XP bonus ("Teamwork"). Social and fun, not a power gain.

### 11.4 Failure moments (make it feel alive, never frustrating)
- **Missed toss** → kite dips, bumps the parapet, flutters back → retry (no durability loss).
- **Snag on a cable** (Cables trait roofs, or a bad tug toward a cable) → "Untangle!" mini-game: swipe left/right 3 times, costs ~3 s.
- **Torn kite** (durability < 30%): optional "Patch" step if the player has a patch kit → +25% durability (crate item, spec 7.7).

### 11.5 Short prep (respawn, after roof hopping, Duel rounds 2+)
- 8–12 s: steps 1, 4, 5 only (kanni already tied); helper only if a teammate is there, otherwise solo hand launch.
- Duel: round 1 = full prep for both players, rounds 2+ = short prep, both players always get the **same prep timer**.
- FFA respawn: short prep replaces the current 5 s respawn launch.

### 11.6 Camera & presentation
- Steps 1–3: close cinematic camera (over the shoulder, depth of field on High).
- Step 4: wide shot showing both the player and the helper with the line between them.
- Step 5–6: camera rises behind the player following the kite, then settles into Shoulder mode.
- Sounds: knot rustle, paper flutter, helper shout "Chhoro!" (localized voice line), dhol builds up, crowd cheer on a Perfect.
- Other players' preps are visible on their roofs (animations replicated as a state + timestamp, not frame by frame).

### 11.7 Network & code
- New `LaunchPrepController` in `Core/Match` (pure C#, unit-tested): state machine `PickKite → TieKanni → TieLine → Toss → Tunke → Climb → Flying`, inputs are timestamped taps, server/host evaluates the timing windows and results.
- `MatchSimulation`: replace the `Launch` state with `Prep` (full/short), feed results into the kite's initial height and drift.
- `CharacterView`: plays prep anims from the replicated prep state.
- Bots: prep results by difficulty (Easy mostly Good/Off, Hard mostly Perfect).
- Acceptance: a new player understands every step without text explanation (icons + one-word hints); full prep never exceeds 25 s; short prep never exceeds 12 s; results identical on host and client.

## 12. Graphics quality targets

- Art direction: **premium stylized** (bright, clean, readable) — not photo-real. Sky is the hero; the goal is to look better than other mobile battle games on a phone screen.
- URP settings: SRP Batcher on, GPU instancing for props/houses, baked lighting for static arena where possible, one real-time directional light with soft shadows (High only).
- Post-processing (Volume, by quality tier): Bloom, Color Adjustments (warm), Tonemapping ACES, Vignette light; High adds Depth of Field in lobby/wardrobe and prep close-ups.
- Characters: 8–15k tris each; LOD1 at 50% for other players beyond 30 m.
- Performance budget: ≤ 150 draw calls in match on Medium, 60 FPS on mid-range, 30 FPS on 3 GB RAM phones. Use Addressables for outfits/skins so the install stays ≤ 150 MB.
- Respect the existing quality tiers in spec v1.2 section 15.
